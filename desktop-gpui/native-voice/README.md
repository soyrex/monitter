# Native voice prototype

This is an experimental local Swift child process. Rust retains ownership of agent tasks, identity, turn decisions and authorization. No microphone is opened at launch or during `load`. `start` requests microphone permission and obtains an exclusive per-user `flock` held until stop or process exit. It creates one AVAudioEngine with input voice processing enabled and routes the player through its output mixer, giving the system voice processor a rendered output reference. This is a request to enable Apple voice processing, not evidence of measured echo rejection. On route change capture stops and an error is reported; the caller must stop the old epoch and create a new one. No hosted APIs are used.

## Build and assets

On Apple silicon with macOS 15 or later, the normal macOS `npm run build:gpui` package builds the pinned Swift helper with SwiftPM using the matching debug or release configuration and copies it and its resource bundle into the app before signing. The build fails if the helper build or its resources are unavailable; it does not download model weights. Other macOS hosts still build the desktop, with a warning and build metadata indicating that local voice is omitted; the pinned Phonon framework has no macOS x86_64 slice. Linux desktop packaging is unchanged. The model cache defaults to `~/Library/Caches/Monitter/VoiceModels`, and `MONITTER_VOICE_MODELS` can select another absolute directory. The prototype launcher uses the same default.

From the repository root, run `python3 scripts/voice-native-download.py` to prepare the model cache. The prototype launcher uses the helper and resources from the selected packaged app by default; `--no-build` selects the latest existing debug package. For standalone helper development, run `swift build --package-path desktop-gpui/native-voice -j 3`. Set `MONITTER_NATIVE_VOICE_HELPER` to the absolute path of that executable to override the packaged helper for a preview; its `FluidAudio_LuxTtsG2pResources.bundle` must be beside it.

On 2026-11-04, an Xcode package build linked two Rust static libraries with duplicate `_rust_eh_personality` symbols and failed. The SwiftPM build linked successfully and its staged helper passed the bounded playback-completion probe; use that path if the Xcode build encounters the same failure. The downloader uses a pinned Hugging Face model commit and verifies every file's SHA-256 or git blob hash, and verifies the official Phonon 31M English release archive against its published SHA-256 before extraction. Models live by default at `~/Library/Caches/Monitter/VoiceModels`; Core ML creates device compiled files beside the Phonon packages. The Swift packages pin FluidAudio `ee78635d23d52379117554ba72358b65a0612447` and xn-ptts v0.6.0 commit `95bf24d1ca5e94f0f62abe588b1ccb6f093bcc9c`, whose binary target has its upstream SHA-256 in the manifest. Phonon 31M weights are Apache-2.0; Parakeet weights have NVIDIA Open Model License terms. Model weights remain external downloads. The packaged helper includes the pinned Swift dependencies and their license notices.

## JSONL protocol

One JSON object per line on stdin; one object per line on stdout. Commands have `type`, UUID `sessionId`, UUID `epoch` and nonempty `requestId`. Epochs must not be reused after `stop`. Maximum command size is 16,384 UTF-8 bytes. The owner must continuously drain stdout, discard any event with a stale identity, and stop the child on lease loss or transport failure. The executable only handles one session at a time; models remain warm after stop. `load` requires absolute `modelsPath`. The first load runs one second of synthetic silence through the recognizer and resets its state before returning `ready` with `status: loaded` and `loadMs`; no microphone is opened for warm-up. `start` returns `ready` with `status: started` and `voiceProcessing: true` only when the engine starts. `stop` stops capture and playback, closes the input gate and returns `ready` with `status: stopped`; recognizer cleanup continues in the background, and a new load is rejected as busy until cleanup completes. EOF also stops.

`mute` takes `muted: true|false`. A `muted` acknowledgement means the input gate is closed and queued input discarded; the in-flight recognizer call and reset can still be completing in the background. An unmute waits for that cleanup before opening the gate and acknowledging `unmuted`. If cleanup takes 20 seconds, it reports `recognizerBusy` and input remains muted. A stop or a new mute supersedes a pending unmute with a request-scoped `superseded` error. Repeated mute and unmute commands are acknowledged without creating extra input consumers; only one unmute may be pending at a time. `speak` takes a strictly increasing unsigned `generation` and nonempty `text` of at most 4096 UTF-8 bytes. `pauseSpeech`, `resumeSpeech`, and `cancelSpeech` take the current `generation`. New speech cancels any old generation. Cancel and stop immediately stop the player, invalidate the generation and cancel synthesis. The player receives at most six 80 ms chunks and generation blocks while paused. On an input-activity onset the helper pauses the player before sending `audioProgress` status `paused`, then `inputActivity` with `active` and RMS `level`; the owner decides whether to resume or cancel. RMS is an unvalidated heuristic and may respond to speaker echo, noise or coughs. `audioProgress` includes generation and status `started`, `paused`, `resumed`, `completed`, `cancelled`, or `alreadyFinished`. The latter acknowledges a pause, resume, or cancel for a known finished generation without affecting a newer generation; unknown generations are errors. Completion means the player reports data played back, not that a person heard it.

Streaming transcripts have `type: transcript`, UUID `utteranceId`, `text`, `isFinal`, and an increasing per-utterance `revision`. Partial text is provisional. The EOU callback determines final text; this component does not submit an agent task. Errors include `code` and `message`, and command errors include `requestId`. Every session event carries `sessionId` and `epoch`. Input queue overflow reports an error and stops rather than silently dropping speech. Model and microphone errors are surfaced. Route recovery, permission prompts, local VAD reliability, acoustic echo rejection and Bluetooth/device behavior must be tested on actual hardware; this helper is not a production-ready voice path.

## Synthetic verification

`swift test --package-path desktop-gpui/native-voice --scratch-path artifacts/native-voice-build -j 3` runs queue checks. To exercise the pinned local models without a mic, generate a synthetic file using `say -o /tmp/monitter-voice-synthetic.aiff 'Hello there. This is a local voice test for a conversation assistant.'`, then set `VOICE_MODELS` to the absolute models directory and `VOICE_FIXTURE` to that file when running `swift test`. The model test reports load times, synthetic speech throughput and incremental ASR results. Timings are local observations, not a guarantee of real-world speech accuracy or end-to-end conversation latency.

For protocol testing only, `MONITTER_VOICE_TEST_SINK=1` enables `start` with `testOnlyNoAudio: true`. This opens no audio device, and `ready` explicitly reports `voiceProcessing: false` and `testOnlyNoAudio: true`. Its `generated` event denotes synthetic TTS generation, never playback. The test is `python3 scripts/voice-native-jsonl-test.py <absolute-helper-path>`. Do not enable this environment variable for an interactive voice session.

For an explicitly authorized physical probe, `MONITTER_VOICE_DIAGNOSTICS=1 python3 scripts/voice-native-physical-test.py <absolute-helper-path> <absolute-models-directory>` forwards stage timing to stderr without PCM or transcript text. The probe opens the microphone and has a 45-second capture kill timer. On 2026-11-03 the built-in MacBook microphone/speaker route passed start with voice processing, playback controls, mute, unmute and stop; no human utterance was supplied, so transcription, conversational behavior, and echo rejection were not established. This does not establish Bluetooth-route behavior.

For a separately authorized playback-completion probe, run `python3 scripts/voice-native-physical-test.py --playback-completion <absolute-helper-path> <absolute-models-directory>`. It starts the audio engine, waits for mute acknowledgement, then plays a fixed short phrase to the player's completion callback and cancels a second fixed phrase while active. The same 45-second capture kill timer applies. This mode suppresses helper stderr, prints no transcript text or PCM, and does not submit anything to an agent. Completion is component-level evidence of the player's callback; it does not establish that a person heard the audio, its quality, or playback through the app.

Continuous capture probe: `MONITTER_VOICE_DIAGNOSTICS=1 python3 scripts/voice-native-physical-test.py --capture-soak-seconds 65 <absolute-helper-path> <absolute-models-directory>`. The duration must be 30–90 seconds. It drains events continuously, fails on helper errors, then mutes, stops and reaps the helper. An independent duration-plus-30-second kill timer bounds capture. Only event counts/control metadata are printed; no microphone PCM or transcript text is retained or sent to an agent. Do not equate a quiet-room pass with conversational accuracy.
