# Streaming state and transcript access

Messages, events, channel messages, captured subagent transcripts and the usage ledger use persistent ordered histories. Cloning a mutation candidate shares tree nodes. Known-message updates use an indexed mutation guard; append and point-update deltas describe only affected positions. SQLite writes that delta inside its existing transaction, then the service publishes the new revision. A rejected mutation leaves both the committed state and UI revision unchanged. IDs remain unique at the persistence boundary.

Public JSON histories retain the existing array shape. SQLite schema v2 separates channel message rows from channel metadata; opening a v1 database migrates it transactionally, and older apps reject v2 rather than misreading an empty metadata array as a lost transcript. General structural operations, including retention/reordering and legacy raw mutable iteration, take the complete differential path. Startup/import can build indexes once. The hot Codex/ACP message update path uses identity lookup and a tracked guard; arbitrary raw indexed mutation may need a lazy index rebuild and is not the streaming API.

`get_ui_delta({revision?})` is an owner/native read. An initial request, process-epoch mismatch, expired journal, or structural transcript edit returns a bounded snapshot. It contains the latest 64 messages per task and per channel, plus bounded activity. A current revision returns neither snapshot nor delta. A retained older revision returns a delta with its exact `fromRevision`, current metadata, changed messages and explicit message deletions. Clients must reject a delta whose base is not their cached revision. Deltas never authorize or repeat mutations.

The journal retains at most 128 committed revisions and 8 MiB of encoded task and channel message changes. A single larger change becomes a reset marker. Revisions with no message changes still participate in the sequence. For unchanged channel message arrays and captured subagent transcript entries, `retainedChannelIds` and `retainedSubagentTranscriptIds` tell the client which cached bodies to keep. Changed channels carry explicit message upserts/removals; a structural replacement sets `reset` and replaces only that channel with its latest 64 messages. Other metadata replaces the current view, including deletions. Streaming work therefore depends on affected rows and workspace metadata, rather than all historical message/event/usage bodies.

`get_task_messages({taskId,beforeId?,limit?})` returns chronological records, an exclusive stable message-ID cursor in `nextBeforeId`, and the observed revision. The default page is 64 messages and the maximum is 100. The cursor must belong to that task and still exist; otherwise the caller gets a visible refresh error. Appends do not invalidate an older cursor. Per-task ordered indexes and binary search locate deep pages without scanning unrelated history. A page records a snapshot in time, so clients retain newer already-observed versions of a message when a page races live updates.

`get_channel_messages({channelId,beforeId?,limit?})` applies the same page bounds and stable exclusive cursor within one channel; its reply also identifies the channel. Native and owner-LAN consumers validate channel and revision before merging. Loaded page overlays remain frozen only while the reader is detached and are cleared on follow release so authoritative edits/deletions can take effect. Individual inline subagent transcripts remain capped at 200 entries; metadata work still depends on the number of tasks, channels and sessions.

The legacy `get_ui_snapshot` protocol remains available to older clients. Controller/visitor protocol v1 has no history paging action: its owner-side adapter reads the complete transcript with bounded activity, separately from the desktop's paged cache. Visitor filtering and revocation checks still run before returning that projection. Diagnostic event pages remain available through `get_task_events`; full event detail remains explicitly loaded. The compact live activity projection examines at most 512 recent indexed events per task, keeps up to 60 useful events per task, and caps the aggregate at 300. It omits log/output entries; it is a bounded activity view, not the durable journal.

Validation uses synthetic temporary stores only. `service_latency_benchmark` measures real native mutation, UI projection, delta encoding and SQLite storage against large fixture histories. It does not open a model session or read the user's database. Its results are machine-specific evidence, not a latency guarantee.
